## 验收与执行顺序

1. 冻结官方初态文件、抽取向量、BDDL、代码、模型和新噪声的哈希。拒绝重复初态或已成功初态，不静默替换初态。
2. 两机各生成 16 个新初态的完整候选图与可见性；两机共同覆盖 32 个初态。渲染前后物理状态必须一致。
3. 两机各运行 192 次验收：事前选择的 8 个任务初态 × 3 视角 × 2 噪声 × 2 模型 × 2 重复。与旧试验是不同起点和噪声，不复用旧门槛结论。
4. 每条闭环真正的第一次模型请求，其外部图、腕部图、本体数组、内外参必须与该初态/候选的指标渲染逐项哈希相同；任务结束再次核查外部位姿未变。初始化的 10 步也在轨迹签名链中。
5. 同键的两机、两重复完整输入—动作—逐步物理轨迹、成败及步数必须一致，否则阻止主矩阵，不能降低门槛后静默继续。
6. 为两模型计算同一批候选输入的 8 初噪 Accel。完成后进入四轮正式矩阵。

## 主分析：一份矩阵，四种视角使用层级

定义 `Y[m,t,i,c,n]` 为一次实际整任务闭环的二元成功标签，先计算 `q[m,t,i,c] = mean_n Y`。

| 项目 | 固定汇总规则 | 解释边界 |
|---|---|---|
| 规范视角 | 对 `c=canonical` 的 q 在初态、任务上等权汇总 | 共同参考 |
| 全局经验最佳固定候选 | 先对全部初态、任务平均 q，再在 c 上取 max | 事后同一相对目录位姿规则，不保证不同场景是同一世界坐标 |
| 每任务经验最佳固定候选 | 每任务先平均四初态，再选 c | 事后按任务的固定相机摆放参照 |
| 每初态经验 Oracle | 每个初态先对 32 噪声平均，再选 c | 事后候选空间参照，不是已经实现的可部署选择器，也不是中途动态切相机 |

四者都包含规范视角；相同总体、任务权重、候选、噪声和时限。不得逐个噪声选赢家，不将旧快照百分比拼在同一比较表。经验 max 有有限样本选择偏差，所以不能直接称为真实期望成功率上限。论文问题是否成立，要同时看头部空间、初态/任务异质性、选择方法的留出收益与不确定性，而不靠更换统计总体制造提升。

## 指标、选择器与复用

预先保留的规则：最低平均 Accel、最高外部任务实体可见性、Accel Top-10 内最大外部可见性；并列时按候选目录顺序确定。外部可见性与双相机平均可见性分开，不将腕部可见性叫外部视角信息。方法均允许选择规范视角。

开发仅用每任务初态 0、1，初态 2、3 的闭环标签不得参与规则和超参数选择；这是选择器的初态留出，非任务留出。可查询全部候选图/Accel 的条件必须明确写出，不能称为静止单实体相机免费获取了其他候选图。

可从完整矩阵复用测试初态上被选候选的实际闭环标签，无须为每种离线指标机械重跑全部候选。最终若进行独立新噪声确认，只评少数已冻结方法和共同基线；另立预算，不自动重建 97 候选全矩阵。动态切相机和主动获取不在本轮。

优先分析：相同初态下两模型的成功率/Accel 空间切片；两模型成功率差值图；各规则相对规范视角的逐任务收益；经验 Oracle 与方法差距。使用实际离散候选坐标，不把插值当实测连续 SE(3)。统计区间需考虑初态嵌套于 8 任务的结构，并单独展示逐任务差异。

## 时间与状态

### 2026-09-09：仅调度优化

用户授权优化速度但不影响评测。静态 `todo[worker::32]` 会使短任务 worker 先结束，长任务只剩少数 worker 收尾；改为每主机内 32 个 worker 共享 FIFO 队列。主机初态分工、四轮预算、并发上限、16 个策略服务、模型、候选、初噪及去噪、初始化和终止条件都不变，保活不动。

执行扩展目录：`scheduling/dynamic-v1`。`manifest.json` 单独冻结调度代码并绑定原科学 release 哈希；不编辑原 `release.json` 或 `repo`，实际每条 episode 仍执行原冻结入口。已完成记录按原身份验证后跳过，不重写；新调度的 worker/GPU 分配及完成记录哈希另存审计。

原拟暂停自有旧调度进程派发并等待在途回合结束，但两机的暂停状态未可靠维持，首次接管检查主动中止，旧评测继续运行；首次记录保留为 `transition-attempt1-aborted.json` 和对应日志。随后将执行清单中的过渡策略显式修订为可恢复重启：对自有旧控制器发送退出信号，其现有清理逻辑终止自有子进程；完整原子输出保留，切换时尚未完成的少量回合不记为失败，由新调度按原初态、候选与噪声重新执行。不会改变样本总体。`fresh/transition.json`、`gnu/transition.json` 保存实际过渡记录；不对保活发信号。

新调度先额外做每主机 192 次验收，主动改变 worker→GPU 映射，将两次动态运行的完整轨迹与原静态验收逐键精确比较，并核查两机均通过后才继续剩余正式矩阵。新增验收不计入 198,656 条主矩阵。若不一致则停止，不放宽门槛。通过后的 `cross-host-gate-pass.json` 是新调度放行依据，不以代码测试替代实测。

新控制器日志：`scheduling/dynamic-v1/{fresh,gnu}/controller.log`；总体进度仍写原 `hosts/{fresh,gnu}/status.json`。动态控制器是独立后台进程，过渡 tmux 完成后退出不表示评测停止。预计切换和验收约 15–30 分钟；优化收益主要来自减少每轮尾部空闲，具体加速比应以实际完成速度为准，不能承诺两机速度完全相同。
