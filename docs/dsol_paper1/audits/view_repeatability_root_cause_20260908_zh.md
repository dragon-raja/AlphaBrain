# 闭环非逐位复现：根因定位执行记录

授权：用户要求优先定位并解决一致性问题。启动时间 2026-09-08 07:02 UTC。本记录是独立工程诊断，不增加科研样本、不改变训练或候选选择规则。

## 已知与未知

并发基准 192 个状态／视角／噪声键中，32 对 48 有 32 条动作路径不逐位一致，32 对 64 有 33 条；历史 32 对本次 32 也有 35 条。初始物理哈希、对应重规划索引的噪声及最终成功标签全部相同。历史 32 与基准 32 的协议打包与进程映射不同，不是整个执行调度的精确重放。

这既不能把高并发认定为故障原因，也不能把差异直接称为无害数值误差。原哈希日志缺少动作数值和逐步观测／物理状态，不能定位第一次分歧。

## 最小定位实验

- 选择酒瓶入架、杯入微波炉中已观察到较早分歧的各一个诊断样本；加固定奶酪入碗样本作对照。这个选择用于排错，不作研究效应估计。
- 每任务运行两次独立闭环，渲染分别在 GPU 0、1；主策略均为同一个 GPU 0 服务。
- 每次真正的策略调用，额外将完全相同的请求再送入同服务一次及 GPU 1 的同权重服务一次；保存完整动作、图像、本体输入、初噪与数值差异。只有第一次响应进入真实动作队列，额外请求不前进环境、不增加 replan 索引。
- 捕获第一条闭环的动作序列，在两个新进程中固定动作回放，分别用两个渲染设备。回放以捕获轨迹的长度为上限，不在录制动作耗尽后补造动作；不作新的任务成功率估计。
- 每个环境步保存执行动作及执行前后的 qpos/qvel、ctrl、warmstart、力、控制器目标与缓存、本体夹爪命令。每次调用保存实际策略请求图像，不用图像统计量代替像素字节。

## 判读原则

1. 同一请求输出不同：继续定位推理算子、数值后端、服务内部状态；此时不能把原因归给相机。
2. 固定动作仍产生不同物理轨迹：定位初始化、控制器或仿真数值路径。
3. 物理状态相同但图像不同：定位渲染及观测生成。
4. 确定最早分歧及幅度后，再决定修复实现还是建立有科学依据的数值／行为等价检验；不直接用“成功率没显著差异”替代等价证明。

## 根因证据（07:39 UTC）

已将本次观察到的最早非确定性定位到 **MuJoCo/EGL 多重采样抗锯齿渲染路径**，而不是 Flow 初噪对齐、相同输入下的模型输出或固定动作下的物理演化。这里不进一步声称已经定位到某条显卡驱动指令。

| 检查 | 实际结果 | 能支持的判断 |
| --- | --- | --- |
| 原渲染协议下，同一请求重复送入同服务及另一 GPU 的同权重服务 | 790 次比较，动作全部逐位相同 | 这些捕获请求上的模型推理可重复；不是所有算子的普遍确定性保证 |
| 两个新进程执行同一固定动作序列 | 酒瓶 300 步、杯子 254 步、奶酪 300 步，全部捕获物理／控制器数组逐位相同 | 排除了这些回放中的物理状态恢复和控制器分歧 |
| 酒瓶首次闭环分歧 | 0-based call 22（110 环境步后），腕部 150,528 个通道值中 7 个相差 1；动作随即不同；下一次策略观测才出现物理状态差异 | 观测先变、动作随后变、物理轨迹再分叉 |
| 杯子首次闭环分歧 | 0-based call 14，腕部 6 个通道值相差 1；动作随即不同；物理输入 call 15 才不同 | 第二个诊断实例复现同一因果顺序 |
| 无物理步进、无模型、固定姿态反复渲染 | 默认 offsamples=4 产生多个不同 RGB 帧，差值最大 1 | 非确定性不需要闭环或模型参与即可发生 |

**不能将这称为无害的小误差。** 旧协议杯子 live-a 在第 254 步成功，live-b 在 520 步上限失败。酒瓶两次都失败，但后续动作最大差异约 2。这也说明早先 192 条并发小基准中成功标签相同，不足以证明所有闭环结果等价。诊断样本是有针对性选择的，不能据此估算总体失败概率。

## 修复实现和验收

新增独立入口 [trace_view_noaa_v1.py](../../../scripts/dsol_paper1/diagnostics/trace_view_noaa_v1.py)：在每次创建 MuJoCo 渲染上下文之前显式设置 `model.vis.quality.offsamples=0`，并断言实际 `context.con.offSamples==0`。没有修改全局安装的 robosuite、原 evaluator、模型服务、Flow 初噪、去噪步数、重规划间隔或物理仿真设置。

单独关闭 GL_DITHER、GL_MULTISAMPLE 都没有可靠解决；短暂出现 30 张图一致也不能当作成功，后续 100 次重复已复现差异。只调整 OpenGL 状态开关不是已验证的修复。

| 新渲染协议验收 | 结果 |
| --- | --- |
| 酒瓶固定姿态，GPU 0/1 合计 400 次渲染 | 跨 GPU 只有 1 个图像哈希 |
| 杯子固定姿态，GPU 0/1 合计 600 次渲染 | 跨 GPU 只有 1 个图像哈希 |
| 酒瓶两条完整闭环 | 各 60 次推理、300 步；全部捕获输入、动作、物理／控制器数组逐位一致 |
| 杯子两条完整闭环 | 各 104 次推理、520 步；全部捕获输入、动作、物理／控制器数组逐位一致 |
| 修复后额外同请求推理比较 | 656 次，全部逐位一致 |

验收严格检查完整长度相等，不仅比较共同前缀；没有放宽数值容差。四条新协议轨迹最终都失败，**修复目标是可重复性，不是提高成功率**。这是对两个已知分歧样本、两个渲染设备的有限验证，不是对全部候选／状态／GPU 的无限保证。

## 正式实验迁移边界：尚未自动切换

关闭抗锯齿会改变观察分布，不能假装与旧协议完全等价。例：酒瓶同一静态腕部原始图像中，新旧协议有 25,645 / 196,608 个通道值不同，平均绝对差约 1.007，最大 93；不能将这仅称为原有 ±1 抖动的消除。

因此，**修复已在独立入口实现并通过上述验收，但正式评测仍保持原渲染协议；48 并发加速也尚未重新放行。** 旧冻结 release、performance-choice 和科研账本没有被回写，新协议数据不加入旧 union。恢复旧任务仅保持已授权工作连续，并不表示旧协议已获得逐位确定性保证。

建议下一步先建立明确版本的新渲染协议，在单视角／多视角两个 checkpoint 上运行同一小规模配对桥接验证；同步重渲染该子集的候选图像、重新计算 accel／可见性指标，再做新协议内部的 32/48 并发逐位验收。由此确定哪些图表需要补算及是否值得整体迁移。不得将旧图像指标与新闭环结果混搭，也不应未经确认就重跑全部历史实验。

如坚持沿用旧抗锯齿图像，则必须将渲染视为额外不可控随机源，并另行设计重复闭环／配对统计；仅固定 Flow seed 不再等价于固定整个实验随机性。该路线不是已经通过验收的确定性修复，也不能追认原并发 gate 为通过。
