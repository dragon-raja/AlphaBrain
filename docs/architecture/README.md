# 仓库架构与维护边界

本仓库同时承载 AlphaBrain 框架和 Paper 1 研究，不把二者混成一个实验脚本包。

| 层 | 位置 | 职责与依赖方向 |
| --- | --- | --- |
| 共享基础 | `AlphaBrain/common` | 图像与记录编解码；不依赖模型、训练、部署或研究 |
| 框架 | `AlphaBrain/model`、`dataloader`、`training` | 模型、数据、训练能力；只依赖包内能力和外部库，不反向 import scripts/deployment |
| 研究实现 | `AlphaBrain/research/dsol` | 指标、选择器、统计、可视化、获取工程原语；不 import 脚本或报告 |
| 通用执行控制 | `AlphaBrain/research/dsol/execution` | 不依赖模型的任务身份、动态队列、恢复状态机；通过显式适配器接口调用外层运行能力，不反向 import benchmarks/scripts |
| 执行适配 | `scripts`、`benchmarks`、`deployment` | 参数、运行编排、环境和服务适配；调用核心包 |
| 报告 | `reports/paper1` | 消费结果与图表，负责布局和输出 |
| 人类文档 | `docs` | 设计、协议、结论、执行记录、报告产物；不放可执行 Python |
| 验证与治理 | `tests`、`tools` | 测试、静态边界、发布前检查；默认不申请 GPU |
| 历史研究 | `archive` | 原源码与迁移证据；不作为新实现的运行依赖 |

## 入口与数据分离

论文统一的是资源身份、实验协议、指标与报告，不假定策略后端统一：LIBERO当前使用
AlphaBrain/PyTorch，RoboCasa当前使用OpenPI/JAX。后端代码和权重以
`configs/resources/paper1_resources.json` 的稳定ID登记；本机路径单独绑定，禁止
将RoboCasa现有结果重新标注为AlphaBrain结果。跨后端转换属于需要数值/闭环验收的新工作。

仓库根目录保留项目元数据、说明与构建配置。`scripts` 根目录的配置解析、模型下载、环境 smoke 和训练／评测入口是框架公共命令，并非散落的研究算法。新实验命令进入对应职责目录。

模型权重、原始 rollout、缓存数组和凭据不放进源代码包。实验目录的冻结 `repo/`、release、旧来源哈希不因维护工作重写。公开／私有资产分离规则以 `.gitignore` 和发布前人工审查共同落实。

## 当前明确保留的兼容边界

- Paper 1 原 37 个遗留入口和依赖已迁出，脚本根目录不保留 Python／Shell 或批量转发壳。旧控制进程已获用户授权结束；历史冻结源码身份保留，不应用于新布局。
- CABI 仅保留当前基准和兼容链所需的 12 个文件；其他历史研究整体归档，不按文件名猜测其科学价值。
- 图像工具和配对记录工具各只有一份核心实现，旧导入路径保留薄别名。
- 历史脚本按职责整理并不等于它们全部成为通用 API。需要复用时先抽取接口及测试，禁止复制成另一个版本。
- Paper 1 的 85 个原平铺测试已按职责迁入子目录，共享样例在 helpers；自动检查禁止恢复平铺或测试模块之间互相导入样例。

运行链整体切换需要新源码版本和完整轨迹一致性验收。此次静态／CPU 验证不冒充所有模型、所有机器人环境的运行认证。

## 变更与验收

1. 确认职责、消费者、运行进程及冻结身份引用。
2. 保存原字节和路径映射；先建立测试，再改导入或拆模块。
3. 重构与科学协议变化分开，不能借维护改变任务、初态、噪声、训练配置。
4. 执行仓库检查、相应测试配置、打包与导入验证。
5. 审查 staged 文件中的私有资产、凭据、体积与无关改动，再提交／推送。

命令见 [测试说明](../../tests/README.md) 与 [开发规范](../../CONTRIBUTING.md)。历史迁移收据原样保留，后续迁移通过带前后哈希的新记录建立连续来源链。

## 并行执行标准

新并行实验采用 [执行管理协议](../dsol_paper1/protocols/execution_management_zh.md)。共享协议层不统一JAX/PyTorch模型实现，也不把科学结果校验挤进调度器。后端通过 `Backend` 接口提供启动、身份、停止与结果核查；队列只负责预先冻结的工作所有权和状态转换。

2026-09-30：通用队列和安全CLI已实现并纳入CPU CI。历史LIBERO控制器与当前XR-1冻结副本仍为兼容实现，尚未完成新标准的实际运行准入；不热替换、不冒用旧源码哈希。

## 当前连续 PPO 的复用范围与扩展边界

2026-10-22 核对：连续 PPO 已使用标准队列，实际运行方式是每个模型条件一个中央
CPU 学习器；规范/多视角组使用同机四个采样worker，原生组已通过八个驻留worker准入并完成。不同机器上的模型条件独立训练，各有策略、
优化器、预算与输出目录；这不是跨机器联合更新一个策略，也不是 DDP。
具体科学配置与准入记录见 [连续训练协议](../dsol_paper1/protocols/continuous_training_zh.md)。

| 能力 | 当前实现与复用范围 | 必须隔离的部分 |
| --- | --- | --- |
| 试验身份、源码与资产哈希 | `execution/manifest.py`；训练与评测可共享 | 模型解码、任务、初态与噪声协议由适配器核验 |
| 队列、所有权、失败收尾、显式恢复 | `execution/queue.py` 的 `Backend` 契约 | 评测的独立任务、PPO 的同版回合批次、DDP 的整个进程组不能混用完成条件 |
| GPU 身份与资源检查 | `execution/gpu_guard.py`；可信保活共存、未知占用阻塞、启动前复检 | 各模型实际显存、运行环境及每卡 worker 容量须分别准入 |
| PPO 回合预算 | `execution/rollout_budget.py`；全局预留、调用前记账、失败仍计费 | 当前查询顺序验证固定两条噪声，尚不是任意模型调用的通用账本 |
| 策略版本与优化 | `selectors/continuous_parallel.py`、`continuous_ppo.py` | 仅完整且同版本的批次进入更新；不能套用评测的随到随合并 |
| 模型与环境 | `benchmarks/LIBERO` 等适配层 | 图像处理、动作解码、渲染、任务时限，不进入通用调度核心 |
| 记录与展示 | 训练存档保留原始记录；`reports/paper1` 消费结果并同步 W&B | 奖励曲线与任务成功率分别记录，追踪进程不承担模型执行 |

每轮先发布策略快照，四个 worker 各采集八个完整回合，核对全部 32 回合后中央更新，
再发布下一版。冻结 VLA 仅在单批采样期间驻留，批次结束 worker 退出。
这使版本和失败边界明确，但存在重复加载、进程启动及等待最慢 worker 的开销。
瞬时空卡或 GPU 利用率低不能单独判定失败，也不代表增加卡数就能同比提速。

维护边界已建立，但以下工作尚未完成：

1. **通用进程后端归属。** LIBERO 的 `CollectorBackend` 仍继承
   `benchmarks/Robocasa365/probe_queue.py` 中的 `ProbeBackend`，间接依赖 RoboCasa
   工具。下一次后端重构应提取共同进程生命周期与 GPU 准入实现，两个 benchmark
   只保留命令构造与结果校验；不要复制第三份控制器。先做身份、启动间隙、故障清理的
   等价测试，再做新冻结版本的真实准入，不热替换活跃源码。
2. **驻留采样进程。** 新的 `continuous_resident` 适配器已经接入通用队列与
   `execution/resident_mailbox.py`：跨批保留冻结VLA，显式发布策略版本，拒绝旧版本或
   不完整回合；失联收尾和CPU四/八进程测试已覆盖。GNU四worker冷/热精确准入通过，
   八worker冷/热48条真实准入也已通过，GNU原生组使用8个驻留worker；旧冻结训练保持原批后退出方式。共享邮箱不等于已验证
   跨机传输，不以异步混入旧策略消除等待。
3. **跨机采样与预算存储。** 当前采样器明确只接受单机不同 GPU。跨机需要独立的传输、
   版本与故障准入。当前预算使用文件锁和原子替换；不能仅因共享盘可见就认为跨主机
   锁语义已验证，须验证存储契约或改用单一记账服务。
4. **协议参数与通用设施。** 若未来改变每查询噪声数，应把两条噪声的顺序约束移到显式
   协议参数并单独测试，不能顺带改变当前计费或复用旧准入。

新任务应复用公共契约，保留算法和后端隔离。历史控制器不因目录整理自动获得当前
准入；CPU 调度测试也不等于所有后端已完成轨迹一致性验证。

### 吞吐优化的实施顺序

原生操作模型适配与采样工程优化可以在活跃实验期间准备、做 CPU 验证；实际切换使用
新的冻结源码与独立准入。当前回合、优化器与运行清单不因此改写。

- 先复用日志区分整批墙钟、worker 采样循环和优化耗时。`LiveEpisodes` 延迟加载模型，
  首次模型加载包含在 worker 循环计时内；整批减去最长 worker 循环主要还包含进程启动、
  排队核验与汇总等，不能标成模型加载。细分计时随下一版代码加入，不热改当前采集器。
- 优先实现跨批驻留模型、显式策略版本发布/确认和完整回合提交；保持每次更新 32 回合、
  原初态组成、原噪声、batch=1 与两条评分噪声，不借提速改变 PPO 或推理语义。
- 随后验证单机更多 collector 的收益。保持全局批次不变，例如 8 worker 各采 4 回合；
  这只是待验收拓扑，不是已授权启动配置。固定 32 回合时，24 或 48 worker 不会自动
  形成合理等额分片，不能为填满 GPU 偷改批次或更新频率。
- 再决定是否需要跨机采样或同卡多进程。跨机预算、策略版本与断联恢复分别验收；同卡
  进程数按实测资源和吞吐准入，不能从空闲显存推定速度。不同操作模型优先各占一台机器，
  便于环境隔离与定位差异。

复用范围扩大不代表自动扩充科学预算。工程效率报告使用完整批次耗时、每小时回合/查询、
加载与等待占比及峰值显存；GPU 利用率是辅助观测，不能替代吞吐或一致性结果。

扩规模的工程顺序、任务覆盖与草案预算见[连续训练协议](../dsol_paper1/protocols/continuous_training_zh.md#完整训练收尾与扩规模准备规划不启动)。工程可并行开发，运行切换须新清单准入；不以等待全量评测为由搁置CPU准备，也不以完成通用队列为由跳过模型/环境验收。
